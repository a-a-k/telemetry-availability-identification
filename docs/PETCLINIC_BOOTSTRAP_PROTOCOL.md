# Petclinic: источник, семантика и проверка работающего стенда

Итерация 004. Вопрос до запуска: можно ли получить четыре различимых внешних исхода, согласованную запись при двух репликах Visits и реальные связанные трассы на закреплённой исходной реализации? Ожидается работающий проверенный стенд, полный census 192 попыток на шести технических контролях, обнаружение обеих реплик и точные причины любого отказа проверки. Это подготовка стенда, не восемь стохастических условий и не новая основная серия. Подгонок моделей нет.

Источник: [Spring Petclinic Microservices, commit 3858f9c630cf989bb6809a86edf47c2be78dc9f1](https://github.com/spring-petclinic/spring-petclinic-microservices/tree/3858f9c630cf989bb6809a86edf47c2be78dc9f1), Spring Boot 4.0.1, Cloud 2025.1.0, Java 17. Четыре исходных модуля собираются без изменения Java-кода; неиспользуемые GenAI/Admin не включаются. Точный Docker image, JAR/agent/SQL SHA и стоимость сборки сохраняются. MySQL, Java, HAProxy и Collector закреплены digest в [конфигурации](../configs/petclinic_bootstrap.json). Обновление этих версий требует отдельной версии стенда.

Все три хранилища используют один MySQL/InnoDB с неизменными исходными таблицами, связями и начальными данными. Customers создаёт owners/pets, Visits использует FK на pets. Инициализация SQL выполняется один раз до старта, обе реплики Visits используют одну БД; повторная инициализация в приложениях выключена. БД, Gateway, Customers, Vets и HAProxy входят в зависимости, но не подвергаются целевой инъекции. Их надёжность не доказана равной единице.

Конфигурация эксперимента использует статический [SimpleDiscoveryClient](https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/common-abstractions.html) вместо Eureka/удалённого Config Server: Gateway видит Customers, Vets и HAProxy под исходными service IDs. Это объявленная конфигурация развёртывания. HAProxy распределяет HTTP-запросы между двумя Visits, TCP health check 500 ms, fall/rise=1; connect=500 ms, client/server=3 s, retries=0. Исходный Gateway сохраняет один повтор POST при 503 и стандартные параметры Resilience4j, включая исходный TimeLimiter 10 s. Общий circuit breaker трёх маршрутов заменён отдельными экземплярами по маршруту; это предотвращает перенос открытия Visits breaker на объявленные контрольные операции. `getOwnerDetails` сохраняет свой исходный breaker и empty-visits fallback. Все эти настройки выбираются до наблюдения live-исходов.

Единый внешний deadline **2 секунды** для всей операции, включая чтение и разбор JSON; превышение означает неуспех даже при HTTP 2xx. Каждая попытка получает один request ID и один W3C trace ID, включая неуспех и отсутствие трассы. Исходная native ошибка не определяет внешний успех. Все поля ниже выводятся из закреплённых SQL seeds, не из ответов проверяемого сервиса.

| Операция | HTTP | Требуемый результат |
| --- | --- | --- |
| list_owners | GET /api/customer/owners | HTTP 200, все 10 владельцев с полными исходными полями и точным набором 13 питомцев/типов; допустима перестановка списка. Visits не требуется. |
| owner_details_with_visits | GET /api/gateway/owners/6 | HTTP 200, Jean Coleman, оба питомца Samantha/Max и все четыре исходных визита с точными ID, датой, описанием и petId. Пустой/частичный visits fallback — неуспех. |
| create_visit | POST /api/visit/owners/1/pets/1/visits | HTTP 201 до deadline, правильные id/petId/date/уникальный marker и ровно одна соответствующая запись в общей БД с тем же id. Нет автоматического повтора со стороны драйвера. |
| list_vets | GET /api/vet/vets | HTTP 200, все шесть ветеринаров с точными именами и полным набором специальностей. Visits не требуется. |

Карточка читает неизменного owner 6, запись использует отдельного owner 1/pet 1. Уникальная строка `study-<SHA256(request_id)>` позволяет обнаружить потерю, повтор и запись без своевременного успешного ответа. Независимый SQL-аудитор читает БД после пакета запросов; pending audit не является успехом. Источник `VisitResource → JpaRepository.save` задаёт транзакционную запись до ответа; дополнительно проверяется сохранение этой записи в общей БД. После timeout наличие записи не восстанавливает успех и не доказывает точный момент commit: сохраняется `write_found_without_timely_success`, без недоказанной метки «поздний commit».

Для bootstrap идут normal, только путь a, только путь b, обе реплики paused, обе живы при отключении сети запросов, восстановление. На каждом контроле 8 попыток каждой операции. Неисправные целевые пути должны давать ноль полных карточек/подтверждённых записей, а обе контрольные операции — оставаться доступными. Любой иной результат сохраняется как провал проверки, без выбрасывания попыток. Отключается только `application` network: сети БД и телеметрии сохраняются, Running=true/Paused=false проверяются независимо. После отказа ожидается завершение стандартного открытого состояния circuit breaker, а не изменение его параметров.

OTel Java agent 2.31.1, точный опубликованный SHA, sampling=1, OTLP HTTP/protobuf в закреплённый Collector file exporter. Встроенный Micrometer tracing выключен для исключения второго набора span; это объявленный выбор инструментирования. Нужны реальные SERVER spans Gateway, Visits для успешных требующих его операций, обе service.instance.id и чистый native parse. Полный request census сохраняет также ошибки/недостающие трассы; успешность bootstrap не утверждает полноту будущего сбора. Bootstrap обязан показать, что такая комбинация Boot/agent действительно работает.

Все сборки, Docker, нагрузка и native parsing выполняются только GitHub Actions. Локально — SQL/source inspection и маленькие искусственные semantic tests. Raw/native/image artifacts хранятся 90 дней; компактные доказательства после проверки переносятся в Git. До завершения bootstrap новый runtime не объявляется квалифицированным. Следом — восемь стохастических условий Petclinic с длительностями нового плана, затем заморозка общей серии 240 кампаний/800 operation cells.
