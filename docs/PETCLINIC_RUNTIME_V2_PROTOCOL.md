# Petclinic v2: согласование с публичным DTO и конфигурацией tracing Boot 4

Вопрос следующей итерации: проходят ли все зафиксированные semantic/fault/native controls на уже построенном приложении, если исправить неверно описанные поля DTO и отключение встроенного tracing? Ожидаются 192 учтённых контрольных запроса, корректная запись общей БД и подтверждённая native связь обеих реплик. Это preparation, без fit и main campaigns.

Запуск с прямым JDK, 34199064678/head 591e5760a0bc4802cec660c24bf12c30fd2ee7e8, успешно собрал исходный Petclinic и image. Warmup сохранил 243 попытки и остановился через исходные 420 s: list_owners/card получили HTTP 200, но oracle отвергал их значения; list_vets проходил. До fault-control пакета выполнение не дошло. Причины установлены по исходному Java и сохранённым последним трём ответам:

1. Customers `Pet.birthDate` — `java.util.Date` с `@Temporal(DATE)`, без `@JsonFormat`. Реальный JSON содержит UTC midnight timestamp, а SQL-derived fixture задавал только дату. v2 нормализует **только birthDate**: исходный YYYY-MM-DD либо тот же день с 00:00:00, нулевой дробной частью и Z/+00:00. Иные день, время, offset, тип значения и невалидная дата отвергаются.
2. Gateway [PetType](https://github.com/spring-petclinic/spring-petclinic-microservices/blob/3858f9c630cf989bb6809a86edf47c2be78dc9f1/spring-petclinic-api-gateway/src/main/java/org/springframework/samples/petclinic/api/dto/PetType.java) — record с единственным `name`. Карточка не может вернуть type.id. v2 проверяет точное имя типа в карточке, а list_owners по-прежнему требует и ID, и имя. Все owner/pet/visit fields, четыре visits, deadline и exactly-once запись остаются обязательными.
3. `management.tracing.enabled=false` не отключил встроенный tracing Boot 4: service logs содержат Zipkin exporter connection errors и Micrometer tracing handlers. Используется [Boot 4 property](https://docs.spring.io/spring-boot/4.0/appendix/application-properties/index.html) `management.tracing.export.enabled=false`/`management.tracing.export.zipkin.enabled=false`, а BraveAutoConfiguration и MicrometerTracingAutoConfiguration явно исключены через документированный Spring auto-configuration механизм. Наличие этих точных классов проверено в исходниках Boot v4.0.1. OTel agent/collector сохранены. Фактическое отсутствие конкурирующих exporters и native связи проверяются в новом запуске.

Исходные v1 module/config/workflows не меняются; v2 имеет отдельные module/config/workflow. Изменение публичного oracle проверено искусственными partial/fallback/wrong-type/wrong-date/timeout/duplicate controls. Исправлен также только способ запуска локальных тестов: новые тесты используют принятый проектом unittest, без отсутствующей в CI зависимости pytest. Старый CI import failure сохранён как инфраструктурный дефект проверки, не scientific result.

Образ **не пересобирается**. Закреплён artifact 10045092166 (`petclinic-build-34199064678`), actual ZIP SHA `28e1aa6966c548376a372cdd05225faf50f57dfd52f0d14509aea52249438a25`, 456 549 451 байт; build-manifest SHA `f8fba7dc1d272ec412674d957b41af87830b2ab87cac73bc8c32bd777b1be925`, Docker image ID `sha256:48a71a0f944e3cda4fcf445a66371d0f76240a6b2603fc2d1c7395779cb71a0d`. Remote restore проверяет API identity/source head, actual ZIP bytes, все 16 manifest files и loaded image ID. Локально только compact evidence, source и bounded controls.

Проверяются заново все четыре операции во всех шести deterministic controls, затем native census; thresholds и fault sequence остаются исходными. Warmup v1 не переименовывается в main campaign и не подмешивается к будущей series. Даже успешный v2 bootstrap не заменяет технический пакет восьми stochastic условий. Все 240 новых campaigns/800 operation cells и prospective candidate freeze остаются следующими обязательствами author plan.
