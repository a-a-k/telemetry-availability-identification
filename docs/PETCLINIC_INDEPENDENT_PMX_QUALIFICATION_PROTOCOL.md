# Независимый PMX: observed database CLIENT constructs и Petclinic technical package

Вопрос до PMX/Palladio runs: сохраняет ли новая DB-client projection исходные IDs/parents/times/errors, представляет ли общий observed database endpoint одним компонентом и проходит ли exact extraction/solver controls? Ожидаемые результаты: 2 новых artificial cases × 2 variants × 2 solver passes = **8 известных oracle answers**, затем полный census **32 application-operation cases / 64 variant slots** на восьми technical acquisitions. Forecast либо explicit absence для каждого slot. Test/evaluator данные не загружаются; main campaigns=0. Accuracy/sign не является gate.

Наблюдаемое основание: calibration-only construct inventory run 34205318062. Java agent 2.31.1 экспортирует MySQL `CLIENT` kind 3 с db.system=mysql, server.address=database, server.port=3306, db.name=petclinic. Customers даёт SELECT owners/pets, Visits — SELECT/INSERT visits. Это наблюдения вызывающей стороны, не server instrumentation MySQL. В Vets после warmup действует cache: отсутствие SQL spans в конкретной calibration не доказывает независимости сервиса от БД.

`pmx_database_client_adapter.py` — отдельная версия M9U request projection. Она выбирает native SERVER spans и MySQL CLIENT spans с полным явным peer identity. Один endpoint `(system,address,port,database)` получает одно детерминированное component/instance identity независимо от caller/Visits replica. CLIENT сохраняет native kind и server=false; original NativeSpan целиком находится в audit. IDs, parent references после прежнего ancestor contraction, timing, errors и весь внешний request population сохраняются. DB operation представляет наблюдаемый клиентский вызов и его совокупную ошибку, не отдельную вероятность внутреннего отказа DB server. Неполный peer identity отвергается явно. Затем применяется unchanged M9X full caller-context identity; loops, PMF и error bridge прежние.

| Новый construct control | Independent inclusive oracle | Conditional-local oracle | Дополнительная проверка |
| --- | ---: | ---: | --- |
| database_propagated | 0.576 | 0.8 | Native CLIENT остаётся CLIENT, DB failure передаётся через parent; IDs/times/errors сохранены. |
| shared_database_two_callers | 0.59049 = 0.9^5 | 0.81 = 0.9^2 | Два разных caller contexts используют один DB component, последовательность calls сохранена. |

Во втором control эмпирический внешний success равен 0.9 из-за коррелированных ошибок; oracle 0.81 проверяет независимое serial composition решателя и **не** объявляется идентификацией этой независимости из данных. Бounded negative control missing peer должен завершаться explicit unsupported. Прежние M9S 16 positive controls, M9U request mapping controls и M9X context/PMF qualifications сохраняются; они не запускаются как новая программа общей отладки.

Информационная граница: отдельные source jobs проверяют retained learner archive и создают самостоятельный PMX artifact ровно с calibration requests, calibration native spans, manifest, source hashes и seal. В нём нет baseline outcomes, health, нашего graph, q, parameter estimates или predictions. PMX extract job скачивает только этот artifact; ему не передаются наши model artifacts. Поле wrapper error выводится из внешнего **calibration** verdict для того же complete business event. Сам PMX Java читает только Options и projected observed traces. Его параметры извлекаются штатно из собственных данных. Ни один evaluator artifact не загружается до candidate freeze.

Проверки extraction: exact operation/component/edge/error-rate PCM comparison, variable-hex native inventory, каждый trace reconstructed once, exact reconstructed time bounds, zero unresolved records. Inclusive native errors не меняются. Conditional-local создаётся только при observed propagation compatibility и положительном denominator; swallowed child или lack of support дают отсутствие прогноза. Для каждого подготовленного PCM применяется только ранее квалифицированный containment/PMF bridge.
